# Plano — Mapa Fatia 1: "o mapa se explica"

Data: 2026-07-27. Base: `docs/specs/2026-07-27-mapa-tatico.md`. Sem git, sem deps novas.

## Decisões (grilling)
- **Filosofia: assistido.** O app informa, nunca barra. Nenhuma economia de ações entra na engine.
- **Persistência: snapshot JSON** da batalha inteira (não tabelas normalizadas).
- **Turno na grade: não.** A grade nunca muda de largura; o turno é marcado só na legenda.
- **Legenda: trunca nomes** e o app avisa quando a mensagem se aproxima de 2000 chars.

## Por que essa fatia
Dois problemas concretos de hoje:
1. No Discord o jogador vê `3` e **não sabe quem é** — a legenda é digitada à mão.
2. A batalha inteira vive em `Mutex<Batalha>` na memória (`lib.rs:33`): fechar o app perde combatentes, pools, iniciativa, cooldowns e posições. Numa sessão de 4h isso é perda real.

## Fatos verificados
- `Estado` (`domain/batalha/mod.rs:41`) já é `Serialize + Deserialize` e **não** contém o RNG. Snapshot é quase de graça.
- `Batalha` = `{ estado, dado: Box<dyn Dado>, undo_stack: Vec<Estado>, proximo_id }`. Só `estado` + `proximo_id` precisam persistir.
- `render_discord(m, pecas: &[(u16,u16,char)])` (`domain/mapa/render.rs:15`) tem só **2 chamadores**: `lib.rs:604` e `discord/mod.rs:653`. Mudar a assinatura é contido.
- Guard de 2000 chars já existe (`excede_discord`, `render.rs:81`), aplicado só no caminho do Discord — não no preview.
- Última migration: `0006_config.sql` → a nova é `0007`.

## Escopo

### Parte A — Persistir a batalha
1. `migrations/0007_batalha_ativa.sql`
   ```sql
   CREATE TABLE batalha_ativa (
       id            INTEGER PRIMARY KEY CHECK (id = 1),
       estado        TEXT NOT NULL,
       proximo_id    INTEGER NOT NULL,
       atualizado_em TEXT NOT NULL DEFAULT (datetime('now'))
   );
   ```
   Linha única (`CHECK id = 1`): existe uma batalha ativa por vez, igual ao modelo atual em memória.
2. `db/repositorios.rs`: `batalha_salvar(conn, &Estado, proximo_id)` (UPSERT) e `batalha_carregar(conn) -> Result<Option<(Estado, i64)>>`.
3. `domain/batalha/mod.rs`: `Batalha::instantaneo() -> (&Estado, CombatenteId)` e `Batalha::restaurar(estado, proximo_id, dado)`.
4. `lib.rs`: helper único que grava depois de cada comando que muta. **Não** espalhar `batalha_salvar` por 15 comandos — um único ponto de saída.
5. `setup()`: restaura do banco no boot; banco vazio = batalha nova (comportamento de hoje).

**Não persiste o `undo_stack`** de propósito: desfazer é da sessão de trabalho, e serializar N estados inteiros a cada mutação sairia caro. Documentar no código.

### Parte B — Legenda automática + turno
6. `domain/mapa/render.rs`: novo tipo
   ```rust
   pub struct PecaRender { pub linha: u16, pub coluna: u16, pub glifo: char,
                           pub nome: String, pub eh_turno: bool }
   ```
   `render_discord` passa a receber `&[PecaRender]`. Grade sai **idêntica** à de hoje (o glifo continua 1 char).
7. Bloco de legenda abaixo da grade: `1 Barril · 2 Ryoko D. Vio… · 3 Bariarte ◀ turno`.
   Só entra quem está posicionado no mapa. Nomes truncados por um teto de chars.
8. `domain/batalha/pecas.rs`: `pecas_para_render` passa a devolver `PecaRender` (nome + `eh_turno` a partir de `indice_turno`).
9. Atualizar os 2 chamadores (`lib.rs:604`, `discord/mod.rs:653`).

### Parte C — Aviso de limite + log espacial
10. `render_mapa_discord` (preview) devolve também o tamanho; a UI mostra `1870/2000` e fica âmbar/vermelho perto do teto. Hoje o preview não checa nada e o erro só aparece na hora de postar.
11. `Evento::PecaMovida { id, de, para }` no histórico, renderizado como `Bariarte moveu C4 → F4` no `HistoricoDialog`.

### Testes (Rust)
- Round-trip do snapshot: estado com combatentes/pools/cooldowns/posições → salvar → carregar → `assert_eq!`.
- Restaurar de banco vazio = batalha nova.
- Legenda: só posicionados; marca o turno; truncamento respeita o teto.
- Grade permanece byte-a-byte igual à de antes quando não há legenda (não regredir o formato).
- `excede_discord` continua pegando o caso 26×50.

## Verificação
- `cargo test` (97 hoje → ~105) + `cargo build` + `npm run build`, conferidos **no main thread**.
- GUI (usuário): abrir batalha, posicionar peças, **fechar o app e reabrir** → tudo no lugar. Postar no Discord e conferir a legenda com o turno certo.

## Riscos
- **Área de mutação de dados** (regra 15/13): migration nova + gravação a cada comando. Mitigar com round-trip testado e revisão dedicada.
- Formato da mensagem do Discord muda (ganha legenda) — mapas já no limite podem passar de 2000. Por isso a Parte C entra junto, não depois.
- Snapshot a cada mutação = escrita no SQLite a cada clique. Medir: se pesar, passar a gravar com debounce.
